Parte 01Documento de requisitos · v0.1 · 29 sep 2026

Requisitos

App de guardado de webs de inspiración. Estilo Moodmark, en versión sencilla.

01Visión general

La aplicación permite guardar páginas web que resultan interesantes (por su diseño, sus componentes o su estilo) para consultarlas más adelante como fuente de inspiración. Cada web guardada se representa con una captura de pantalla, su enlace, un título propio, etiquetas (tags) y notas personales.

El objetivo de la primera versión (MVP) es cubrir el ciclo básico: guardar, visualizar en mosaico, buscar y agrupar. Funcionalidades más avanzadas, como guardar componentes concretos, quedan para versiones futuras.

Alcance

ÁmbitoContenido
Dentro del MVPFicha de cada web, mosaico principal, búsqueda por tags y por título, colecciones.
Deseable en el MVPSi es viable: captura de la página completa (no solo la parte visible).
Fuera del MVPFuturo: guardado de componentes concretos de una web.

Cada web guardada se representa con una imagen, su enlace, un título propio, tags y notas personales.

El objetivo del MVP es cubrir el ciclo básico: guardar, visualizar en mosaico, buscar y agrupar.

03Cómo se llegó a cada decisión

Las decisiones se tomaron en este orden. Varias cambiaron por el camino al aparecer información nueva; se deja constancia de la opción inicial y del motivo del cambio.

3.1 Sistema de front

  • Análisis de los requisitos: es una herramienta privada detrás de un login (nadie llega desde Google), casi toda la interacción ocurre en el cliente (mosaico, filtros combinados, detalle, colecciones) y probablemente habrá una extensión de navegador.
  • Conclusión técnica: una SPA con Vite. Se descartan Next.js, Nuxt, Astro y SvelteKit en modo servidor porque resuelven problemas que aquí no existen (SEO, primera carga, contenido público).
  • Recomendación inicial: React + Vite, por el tamaño de su ecosistema (masonry, recorte de imágenes para RF-F1, extensiones).
  • Decisión final: Vue 3 + Vite + TypeScript, porque es el framework que mejor conoce la usuaria. Para una app de este tamaño, la soltura con la herramienta pesa más que la diferencia de ecosistema, y Vue cubre todo lo que pide el MVP.

3.2 Backend y dudas abiertas del documento

La usuaria pidió que el backend lo liderase un perfil de ingeniería backend. Las cinco dudas abiertas del documento de requisitos se resolvieron así:

Duda abiertaRespuestaMotivo
¿Local o en la nube?NubeAcceso desde varios dispositivos y un único origen de datos para la web y la futura extensión.
¿Web, extensión, escritorio o combinación?Web ahora; extensión despuésLa web da una app usable antes. La extensión se añade usando la misma API.
¿Captura desde servidor o extensión?Pospuesta a v2Inicialmente: servidor con Playwright y extensión en una segunda fase. Después se decidió aplazar la captura automática (ver 3.4).
¿Subida manual si la captura falla?SíSiempre habrá webs que bloqueen bots o pidan login. En v1 además es la forma principal de tener una buena imagen.
¿Tags libres o sugeridos?Libres con autocompletadoFlexibilidad sin duplicados: se normalizan (minúsculas, espacios) y se sugieren los ya usados.

Lenguaje: TypeScript también en el backend, para compartir tipos y validaciones con el front sin aprender otro lenguaje. Framework: Hono, cuyo cliente tipado permite que el front Vue conozca exactamente qué devuelve cada ruta.

3.3 Login y base de datos

  • Propuesta inicial: Better Auth para el login y Neon como Postgres.
  • Cambio: la usuaria ya conocía Supabase. Se pasa a Supabase Auth y, de paso, a Supabase como base de datos: menos proveedores, y la parte delicada de seguridad (contraseñas, tokens, límites de intentos) resuelta.
  • Supabase se usa solo para el login y como Postgres. El front nunca consulta la base de datos directamente: toda la lógica pasa por la API, que valida el token (JWT) de Supabase.
  • Método: email y contraseña (los magic links son incómodos en una extensión). Registro público desactivado: la usuaria se crea desde el panel.
  • Imágenes fuera de Supabase Storage: el plan gratuito da 1 GB, frente a los 10 GB sin coste de descarga de Cloudflare R2.
Pega conocida El plan gratuito de Supabase se pausa

Los proyectos gratuitos se pausan tras unos 7 días sin actividad. Se reactivan desde el panel sin perder datos. Si llega a molestar, las opciones son el plan Pro (25 $/mes) o migrar la base de datos, que es un Postgres estándar.

3.4 Captura de pantalla: aplazada a la v2

La captura automática necesita un navegador sin interfaz (Playwright + Chromium) en un servidor, una cola de trabajos, control de páginas enormes, banners de cookies y memoria. La usuaria propuso dejarla para una segunda versión, y se aceptó: reduce mucho la complejidad y el riesgo de la v1.

OrdenFuente de la vista previa en v1
1Imagen subida por la usuaria: pegada con Ctrl+V en cualquier parte de la página, arrastrada o elegida del disco. Permite subir capturas de página completa hechas con Firefox.
2og:image de la página: la imagen que muestran las webs al compartir un enlace. Se copia a nuestro almacenamiento para que no se rompa.
3Tarjeta generada con el favicon y el dominio. El mosaico nunca tiene huecos.
Limitación asumida

La og:image suele ser una imagen de marketing, no una captura del diseño. Por eso la subida manual se ha hecho lo más cómoda posible.

Consecuencias: desaparecen Playwright, la cola de trabajos y los estados de captura, y ya no es obligatorio un contenedor con Chromium. La v2 solo tendrá que añadir un proceso que rellene los mismos campos de imagen.

3.5 Diseño visual

Se deja para después de validar la plataforma. La v1 usa un estilo mínimo y provisional: fondo blanco, bordes negros finos y tipografía del sistema en negro.

3.6 Entorno de desarrollo

El equipo de la usuaria no tiene Docker ni la CLI de Supabase. En lugar de exigir instalarlos, se ajustó el plan: en desarrollo, la base de datos y el login van contra un proyecto de Supabase en la nube (gratis), y las imágenes se guardan en disco local. El mismo código usa R2 en producción cambiando solo la configuración.

4.2 Flujo de datos

 Vue ── supabase-js (solo login) ──► Supabase Auth ──► devuelve un JWT
  │
  └── cliente de Hono + "Authorization: Bearer <JWT>" ──► API /api/*
                                                          │ valida el JWT de Supabase
                                                          ├─► PostgreSQL (Supabase)
                                                          └─► Imágenes (disco local / R2)

Al guardar una web:

  1. La API descarga el HTML de la página (con protección SSRF) y lee título, favicon y og:image.
  2. Si no hay imagen propia, copia la og:image, la convierte a WebP y crea la miniatura.
  3. Guarda la web con sus tags y colecciones en una única transacción.
  4. Si la usuaria adjuntó una imagen, el front la sube después y sustituye a la anterior.

05Seguridad

RiesgoMedida
SSRFEl servidor abre URLs que escribe la usuaria. Se bloquean las direcciones no públicas (localhost, redes privadas, metadatos del cloud), comprobándolas al conectar y en cada redirección, con tiempo y tamaño máximos.
API REST de SupabaseLa clave pública del front podría leer las tablas. Se activa RLS en todas ellas sin políticas: ese acceso queda cerrado y la API propia no se ve afectada.
Acceso ajenoRegistro público desactivado. Cada consulta filtra por usuaria y no se pueden usar colecciones de otra persona.
Archivos subidosSe valida el contenido real de la imagen (no la extensión). Tamaño máximo de 25 MB.
Imágenes públicasSe sirven sin login, pero con rutas aleatorias imposibles de adivinar.

01Las piezas de la app

Begiz se compone de cinco piezas. Tú solo ves la primera; el resto trabaja por detrás.

PiezaDónde estáQué hace
Frontapps/web · Vue 3 + ViteLa app que ves en el navegador: el mosaico, los formularios, los filtros. No guarda datos: se los pide a la API.
APIapps/api · Hono + DrizzleUn programa en un servidor que recibe las peticiones del front, comprueba quién eres, lee las páginas que guardas, procesa las imágenes y habla con la base de datos.
Supabase AuthTu proyecto de SupabaseGestiona las cuentas: email, contraseña cifrada y las sesiones.
Base de datosPostgres en SupabaseGuarda las webs, tags y colecciones de cada usuaria.
ImágenesDisco local / Cloudflare R2Guarda los archivos de imagen. En la base de datos solo queda la ruta de cada uno.

Además hay un paquete compartido, packages/shared, con las reglas de validación (qué es una URL válida, cuánto puede medir un título, cómo se normaliza un tag). Lo usan el front y la API, así que las reglas son siempre las mismas en los dos lados.

 Navegador (front)
   │
   ├── login ──────────────────────────► Supabase Auth ──► devuelve un token (JWT)
   │
   └── peticiones + "Authorization: Bearer <token>" ──► API  /api/*
                                                          │ 1. valida el token
                                                          ├─► Postgres (Supabase)
                                                          ├─► Imágenes (disco / R2)
                                                          └─► Webs externas (título, favicon, og:image)
La regla de oro El front nunca toca la base de datos

Todo pasa por la API, que es la única que sabe las reglas. Así la futura extensión del navegador podrá usar la misma API sin repetir nada.

02Iniciar sesión

TúEscribes email y contraseña en /login.
→
Supabase AuthComprueba la contraseña y devuelve un token firmado (JWT).
→
NavegadorGuarda la sesión para que no tengas que volver a entrar.
→
APIEn cada petición valida el token y saca tu identificador.
  • El token es como un pase firmado por Supabase que dice «esta persona es la usuaria X» y caduca pasado un tiempo. La API comprueba la firma con las claves públicas de tu proyecto (apps/api/src/auth.ts), así que nadie puede fabricar uno falso.
  • Si el token falta, es falso o ha caducado, la API responde 401 y el front te devuelve al login.
  • El registro público está desactivado: las cuentas solo se crean desde el panel de Supabase.
  • El router del front (apps/web/src/router.ts) también te manda al login si intentas abrir una página sin sesión, y al volver te lleva a donde ibas.

03Guardar una web

Es el proceso más completo de la app. Empieza en /new (NewWebView.vue) y lo resuelve la ruta POST /api/webs (apps/api/src/routes/webs.ts).

#QuiénQué pasa
1TúRellenas enlace, título, notas, tags y colecciones. Opcionalmente pegas, arrastras o eliges una imagen.
2FrontEnvía los datos a la API. Si has puesto imagen propia, le dice que no descargue la de la página (usePageImage: false).
3APIValida los datos con las reglas de packages/shared: URL http/https, título no vacío (máx. 200), notas (máx. 5000), hasta 30 tags de 40 caracteres. Los tags se normalizan: « Dark  Mode » pasa a «dark mode», y los repetidos se quitan.
4APILee la página con protección SSRF (ver sección 8): título (og:title o <title>), favicon y og:image. Si la página no responde, no pasa nada: la web se guarda igual, sin esos datos.
5APISi toca usar la imagen de la página, la descarga y crea la miniatura WebP (createThumbnail, en lib/preview.ts) y la guarda en el almacenamiento. Si falla, la web queda sin imagen.
6Base de datosEn una sola transacción guarda la web, crea los tags que no existían, los enlaza y añade la web a sus colecciones. Si algo falla (p. ej. una colección que no es tuya), no se guarda nada y se borra la miniatura que se acababa de crear.
7FrontSi elegiste imagen propia, ahora la sube (ver sección 4). Después refresca el mosaico, los tags y los contadores, y te lleva al detalle de la web.
Concepto ¿Qué es una transacción?

Un grupo de operaciones en la base de datos que se hacen todas o ninguna. Así nunca queda una web a medias, por ejemplo guardada pero sin sus tags.

Prioridad de la imagen de vista previa

OrdenFuente
1Tu imagen, subida a mano. Puede ser una captura de página completa.
2La og:image de la página: la imagen que muestran las webs al compartir un enlace. Se copia a nuestro almacenamiento para que no se rompa si la web la cambia.
3Una tarjeta generada con el favicon y el dominio (WebThumb.vue). El mosaico nunca tiene huecos.

04Subir o cambiar la imagen

Ocurre al guardar una web con imagen propia o con «Change image» en el detalle. Ruta: PUT /api/webs/:id/preview.

  1. Tú pegas una imagen con Ctrl+V (funciona en cualquier parte de la página), la arrastras o la eliges del disco (ImagePicker.vue).
  2. La API comprueba que la web es tuya; si no, responde 404.
  3. Valida el contenido real del archivo con la librería sharp (detectUploadFormat). No se fía de la extensión ni de lo que dice el navegador. Acepta PNG, JPG, WebP, GIF y AVIF, hasta 25 MB.
  4. Crea la miniatura: WebP de 800 px de ancho. Si la imagen es muy alta (una captura de página completa), la miniatura se recorta a los 1200 px de arriba.
  5. Guarda dos archivos: la miniatura (para el mosaico) y el original (para el detalle, a tamaño completo).
  6. Actualiza la web en la base de datos y borra las imágenes anteriores, para no acumular archivos huérfanos.

Cada archivo lleva un identificador aleatorio nuevo en su nombre, así que una imagen nunca se sobrescribe: se crea otra y se borra la vieja. Esto permite que el navegador las guarde en caché para siempre.

05El mosaico y los filtros

La página principal (HomeView.vue) pide las webs a GET /api/webs con los filtros activos.

FiltroEn la URLCómo funciona
Buscar por título?search=portfolioBusca el texto dentro del título, sin distinguir mayúsculas. Los caracteres especiales (%, _) se tratan como texto normal. Un índice especial (pg_trgm) mantiene la búsqueda rápida aunque haya miles de webs.
Tags?tags=dark,serifDevuelve solo las webs que tienen todos los tags elegidos (Y), que es lo útil para buscar inspiración concreta.
Colección?collection=<id>Solo las webs de esa colección. Se combina con los demás filtros.
  • Los filtros viven en la URL: si recargas, compartes el enlace o vas hacia atrás, se mantienen.
  • El buscador espera 250 ms después de la última tecla antes de pedir resultados, para no lanzar una petición por cada letra.
  • Las webs salen de la más nueva a la más antigua.
  • Caché (TanStack Query): el front recuerda las respuestas de la API. Al volver a una página ya vista, la muestra al instante. Al cambiar un filtro, mantiene el resultado anterior en pantalla hasta que llega el nuevo, sin parpadeos. Después de guardar, editar o borrar, invalida esa caché para que todo se vuelva a pedir actualizado.
  • La lista de tags del filtro (GET /api/tags) muestra solo los que están en uso, ordenados por cuántas webs los usan. La misma lista sirve para el autocompletado al escribir tags.

06Detalle, edición y borrado

Ver y editar una web

  • El detalle (/webs/:id) muestra la imagen a tamaño completo si existe, el enlace a la web, el título original de la página y el formulario de edición.
  • Al guardar cambios (PATCH /api/webs/:id) solo se actualiza lo que envías. Los tags se reemplazan por la lista nueva, y los que ya no usa ninguna web se borran solos. Las colecciones también se reemplazan, comprobando que todas son tuyas.

Qué se borra y qué se conserva

AcciónSe borraSe conserva
Borrar una webLa web, sus enlaces con tags y colecciones, sus imágenes y los tags que quedan sin uso.Las colecciones (con una web menos) y los tags que usan otras webs.
Borrar una colecciónLa colección y la lista de sus webs.Todas las webs. Solo dejan de pertenecer a esa colección.
Quitar un tag de una webEl enlace; y el tag, si ya no lo usa ninguna web.La web y el resto de sus tags.

Colecciones

  • Se crean desde el formulario de guardar o editar una web (CollectionPicker.vue).
  • En /collections se listan con su número de webs y se pueden renombrar o borrar.
  • No puede haber dos colecciones con el mismo nombre: la API responde 409 con un mensaje que se muestra en pantalla.

08Seguridad

RiesgoCómo se evita
Ver datos de otra personaCada consulta filtra por tu user_id. Si pides una web o colección que no es tuya, la API responde 404 como si no existiera, y no puedes meter tus webs en colecciones ajenas. Los tests de aislamiento lo comprueban en cada cambio.
Acceso directo a la base de datosSupabase permite leer tablas con la clave pública que usa el front. Por eso todas las tablas tienen RLS (Row Level Security) activado y sin permisos: ese acceso queda cerrado. La API se conecta como propietaria y no le afecta.
SSRFLa API abre las URLs que escribes. Alguien podría usarla para alcanzar direcciones internas del servidor (localhost, redes privadas, metadatos del proveedor cloud). lib/safe-fetch.ts bloquea las direcciones no públicas en el momento de conectar y en cada redirección, con un tiempo máximo de 8 s y un tamaño máximo de descarga.
Archivos maliciososLas imágenes se validan por su contenido real, no por la extensión. Un archivo que no es imagen se rechaza aunque se llame .png.
Imágenes públicasSe sirven sin login, pero sus rutas llevan identificadores aleatorios imposibles de adivinar.
Cuentas ajenasRegistro público desactivado. Solo existen las cuentas creadas desde el panel.

Comandos

ComandoPara qué
pnpm devArranca el front (localhost:5173) y la API (localhost:8787). Los cambios en el código se recargan solos.
pnpm testEjecuta los tests de la API y de shared. Unos 25 segundos, sin Supabase ni internet.

Los tests

  • Usan PGlite, un Postgres de verdad que se ejecuta en memoria y se crea con las mismas migraciones. Cada test empieza con la base de datos vacía y nunca toca tu Supabase.
  • Firman tokens igual que Supabase, así que pasan por la validación real del login.
  • Las páginas externas se simulan (test/fake-web.ts): los tests no dependen de que una web real esté disponible.
  • Cubren login, guardado, filtros, edición, borrado, imágenes, colecciones, aislamiento entre usuarias y SSRF: 53 tests en la API y 11 en shared.

Cambiar la base de datos

  1. Se edita el esquema en apps/api/src/db/schema.ts.
  2. pnpm db:generate crea un archivo SQL con el cambio en apps/api/drizzle/. Toda tabla nueva lleva RLS activado.
  3. pnpm test: los tests crean su base de datos con esa migración, así que un error sale aquí antes de tocar Supabase.
  4. pnpm db:migrate la aplica en Supabase. Las migraciones aplicadas ya no se editan nunca.
Antes de dar algo por terminado Verificación mínima

pnpm test y pnpm typecheck en verde (y pnpm build si se toca el front). Cada cambio en la API lleva sus tests. Los commits se hacen cuando tú lo pides, con mensajes en inglés.

Parte 04Plan de despliegue · 14 oct 2026

Plan de despliegue

Publicar Begiz gratis para dos personas y, más adelante, prepararla para más gente.

01Resumen

El plan de arquitectura (parte 02) daba por hecho una API de pago desde el principio. Para empezar a usar Begiz entre dos personas, la usuaria y su compañera, no hace falta: se despliega en dos etapas. El código es el mismo en las dos; solo cambian los proveedores y la configuración.

EtapaPara quéCoste
1 · GratuitaUsarla entre dos personas y ver qué tal funciona0 €
2 · ProfesionalAbrirla a más gente, la vista pública y la captura automática~32 $/mes sin captura
Sustituye

Esta parte sustituye a «Despliegue y costes previstos» (parte 02, apartado 06) y a «Publicación y costes» (parte 03, apartado 10), que se mantienen como estaban.

02Etapa 1 · Gratuita (ahora)

PiezaServicioPor qué
FrontCloudflare PagesGratis para webs estáticas.
APIRender, plan gratuitoEjecuta Node tal cual, con sharp, y no pide tarjeta.
Login y base de datosSegundo proyecto de Supabase, solo para producciónEl plan gratuito permite dos proyectos. Los datos reales no se mezclan con los de desarrollo y las migraciones se prueban antes en desarrollo.
ImágenesSupabase Storage, bucket públicoCompatible con S3: la API ya tiene ese modo. Sin otra cuenta ni tarjeta.

Por qué no Cloudflare Workers para la API. Es gratis y Hono funciona ahí, pero sharp (imágenes) y la descarga segura de páginas dependen de Node. Habría que reescribir parte del backend, y para dos personas no compensa.

Por qué ahora Supabase Storage y no R2. En la parte 02 se eligió R2 porque da 10 GB frente a 1 GB. Para dos personas, 1 GB basta (las miniaturas ya salen redimensionadas), y así no hace falta abrir otra cuenta. R2 vuelve en la etapa 2.

Peajes del plan gratuito

  • Render duerme la API tras unos 15 minutos sin uso. La primera petición después tarda unos 30–60 s; mientras, se ve la pantalla de carga.
  • Supabase pausa el proyecto tras unos 7 días sin uso. Con uso habitual no pasa.
  • Límites aproximados: 500 MB de base de datos, 1 GB de archivos y 5 GB de descarga al mes en Supabase; 512 MB de memoria en Render. Se comprueban al desplegar, porque cambian.
  • Sin copias de seguridad automáticas de la base de datos.
  • La fase 2 (captura) no cabe: Chromium necesita más memoria de la que da Render gratis.

Pasos

  1. Arreglar antes los pendientes que afectan a otra persona: la sesión caducada (401) y el error de carga de colecciones. Añadir un mensaje de respaldo en index.html.
  2. Crear el proyecto de Supabase de producción, aplicar las migraciones y crear a mano las dos cuentas.
  3. Crear el bucket público de imágenes y sus claves S3. El cliente S3 de la API necesita forcePathStyle, que Supabase exige y R2 también acepta.
  4. Crear el servicio en Render con la conexión del pooler de Supabase (la conexión directa solo es IPv6).
  5. Publicar el front en Cloudflare Pages, enlazado con la API (VITE_API_URL y CORS_ORIGIN).
  6. Probarlo de punta a punta con las dos cuentas.

03Etapa 2 · Profesional (futuro)

Se da el salto con cualquiera de estas señales: entra gente de fuera o se activa la vista pública; el arranque lento molesta; empieza la fase 2 (captura); o los datos ya importan lo suficiente como para necesitar copias de seguridad.

Qué cambia al pasar

  • Imágenes a R2: copiar los archivos y cambiar la configuración. La base de datos guarda la clave de cada imagen, no su URL, así que no se toca.
  • Supabase Pro: se sube de plan el mismo proyecto, sin migrar nada.
  • Altas de cuentas: crearlas a mano no escala. Decisión de producto pendiente: invitaciones o registro abierto.
  • Vigilancia: aviso si la API cae y registro de errores del front y la API, con herramientas que tienen plan gratuito.
